## Structural Integrity

### P074 Extends the Existing Provider Boundary Cleanly
**Impact**: Positive

`packages/core/src/llm/provider/chatgpt.ts:153-302` owns WebSocket-specific connection behavior, while `packages/core/src/llm/provider/openai-sse.ts` remains the shared Responses event interpreter. The in-flight changes add an idle timeout, send-failure classification, close code/reason preservation, and wrapped error parsing without leaking WebSocket concepts into `ProviderManager`, runtime configuration, or the cross-provider `StreamFunction` contract.

This is a sustainable boundary for one provider-specific transport. Extracting a generic WebSocket session abstraction now would need to invent common semantics for handshake metadata, ping/pong, retries, and fallback before another provider shares those requirements.

### Message Decode and Close Are Not Serialized
**Impact**: Compounds over time

`packages/core/src/llm/provider/chatgpt.ts:228-249` serializes message decoding through `messageWork`, because `Blob.text()` is asynchronous. However, `handleClose(...)` at lines 255-282 reads `terminalSeen` immediately and does not wait for the queued message work.

A server can deliver a final `response.completed` text frame and then close normally while `webSocketMessageToString(...)` is still pending. The close handler observes `terminalSeen === false`, fails the queue with a retryable network error, cleans up, and terminates before the final frame sets `terminalSeen`. This can turn a successful turn into a retry, potentially duplicating model work when no completed tool call suppresses retry.

Codex avoids this class of race by reading and interpreting each frame sequentially in one async stream loop (`codex-rs/codex-api/src/endpoint/responses_websocket.rs:666-810`). Diligent should preserve the EventTarget API but serialize close finalization behind `messageWork`.

## Cross-Package Coherence

### Existing Retry Ownership Matches Codex Responses Behavior
**Scope**: `packages/core/src/llm/provider/chatgpt.ts`, `packages/core/src/llm/retry.ts`

Codex's Responses WebSocket client treats a connection as one stream and fails fast on terminal transport errors; retry creates a fresh connection rather than resuming frames in place. Diligent follows the same ownership model: `createChatGPTStream(...)` owns one socket and emits a retryable `ProviderError`, while `withRetry(...)` decides whether the whole stream may be invoked again and suppresses retries after completed tool calls.

Adding reconnect or replay inside `createChatGPTWebSocketEvents(...)` would split retry ownership across layers and risk replaying a request after partially visible output. No change is recommended.

### Responses Event Interpretation Remains Shared
**Scope**: `packages/core/src/llm/provider/chatgpt.ts`, `packages/core/src/llm/provider/openai-sse.ts`

Both ChatGPT WebSocket and ChatGPT HTTP/SSE feed parsed Responses events into `handleResponsesAPIEvents(...)` (`chatgpt.ts:388-395`, `chatgpt.ts:474-481`). Transport framing is local; provider event semantics remain shared. This avoids the parser drift that a separate WebSocket event mapper would create.

## Forward Compatibility

### HTTP Upgrade Failures Are Opaque at the Current Transport Boundary
**Horizon**: Breaks when auth, usage-limit, or rollout failures occur during the WebSocket handshake

`createDefaultWebSocket(...)` uses the browser-style `WebSocket` constructor. Its pre-open error and close events do not expose the HTTP upgrade status, response body, or headers. Consequently, `handleError()` and the pre-open branch of `handleClose()` (`chatgpt.ts:251-264`) can only report a retryable network error even when the provider returned a non-retryable 401, 403, or 429.

Codex uses a lower-level handshake and maps HTTP upgrade failures into transport HTTP errors while retaining response headers (`codex-rs/codex-api/src/endpoint/responses_websocket.rs:486-577`). It also reads successful HTTP 101 headers such as server-selected model and turn state (`responses_websocket.rs:517-536`).

The cheaper fix is not a generalized transport framework. Define a small ChatGPT WebSocket connection adapter whose `connect()` result includes the socket and handshake metadata, and whose failure can carry status, headers, and body. Back it with a lower-level client only if Bun's current API cannot expose those values. Keep the injected fake adapter so classification and close ordering remain deterministic in tests.

### No Immediate Need for Proactive Heartbeats or Connection Reuse
**Horizon**: Revisit only after production evidence of idle intermediary disconnects or measurable handshake cost

Codex's Responses client replies to server Ping frames but does not proactively send heartbeats. Diligent's browser/Bun WebSocket API delegates protocol Ping/Pong handling to the runtime, and P074 adds a 300-second idle timeout. That is sufficient unless production traces show otherwise.

Similarly, Codex records whether a connection was reused but the inspected Responses client does not implement an in-file reconnect/resume pool. Diligent should not add pooling until it can define safe ownership across abort, auth refresh, turn-state updates, and retries.

## Novel Perspective

### Frame Ordering, Not Reconnection, Is the Real Reliability Boundary
- **Why no one has seen this**: WebSocket comparisons naturally focus on reconnect, heartbeat, and timeout features. Diligent's use of EventTarget makes message and close callbacks look ordered, but the ordering is lost when message payload conversion becomes asynchronous.
- **Evidence**: `messageWork` explicitly acknowledges asynchronous message conversion at `packages/core/src/llm/provider/chatgpt.ts:167,228-249`, while `handleClose()` independently makes a terminal decision at lines 255-282. The fake socket tests emit string payloads, so `webSocketMessageToString()` resolves immediately and cannot exercise a delayed `Blob.text()` path.
- **Implication**: Reliability work should first make transport event finalization deterministic and test delayed payload decoding. Reconnect machinery would amplify the race by automatically replaying turns whose successful terminal frame was merely late to decode.

## Findings

### F-01 — Concurrent init can delete a bootstrap entry while reporting success

**Disposition**: Act now
**Lens**: Operational correctness
**Confidence**: High
**Evidence**: Every init process uses the same global `.init-staging` directory and deletes it at startup (`apps/overdare-ai-agent/src/init.rs:78-82`, `235-237`). Each staged entry is also named only from the destination basename (`apps/overdare-ai-agent/src/init.rs:90-94`). After copying, `stage_and_swap` deletes the existing destination before renaming the staged entry (`apps/overdare-ai-agent/src/init.rs:103-109`). Callers catch and log this failure while `run` still returns success (`apps/overdare-ai-agent/src/init.rs:207-216`, `248-264`), even though the managed-directory comment says the old copy remains intact. Existing coverage fails only during the pre-destructive copy phase. A current-HEAD stress reproduction launched two simultaneous `init --skip-update` processes against the same fresh bootstrap; in 2 of 20 runs both exited zero while the deployed skill directory was absent, with stderr reporting `Failed to deploy skills/race-skill: No such file or directory`.
**Impact and mechanism**: Multiple Studio windows can initialize the same environment concurrently. One process can remove another process's staged entry; the affected process may already have deleted the destination before its rename fails. The launcher then reports successful initialization with a missing system prompt, product skill, agent, plugin, or other bootstrap asset.
**Smallest responsible action**: Give each init process a unique staging directory and make replacement rollback-safe: retain the prior destination under a unique backup until the staged rename succeeds, and restore it if promotion fails. Preserve per-entry best-effort deployment, but do not claim the old copy is safe unless it is actually retained through the destructive phase.
**Scope and non-goals**: Cover bootstrap file and directory promotion only. Preserve the current `MissingOnly` versus `FullSync` policy, user-created skill/agent preservation, config preservation, and best-effort continuation across independent entries. Do not redesign runtime bundle installation or add cross-process locking around all launcher work.
**Verification**: Run two real init processes concurrently against both missing and existing file/directory entries and prove the final entry is always complete. Inject a failure after the prior destination has been displaced and prove rollback restores it. Preserve config and user-created skill/agent tests.
**Why now**: This range explicitly introduces atomic bootstrap deployment and concurrent-launch recovery. Multi-window Studio startup and fresh releases exercise this path today; leaving it unfixed makes the new safety claim false and can silently remove product-owned bootstrap behavior.
**Delivery**: Created issue #380 — https://github.com/overdare/diligent/issues/380

### F-02 — MCP catalog ownership does not follow the active Studio target

**Disposition**: Act now
**Lens**: Ownership | Contract
**Confidence**: High
**Evidence**: `RouterState::catalog()` always selects the newest live, or newest stale, registry catalog globally (`apps/overdare-ai-agent/src/mcp_router.rs:56-63`; `apps/overdare-ai-agent/src/studio_registry.rs:185-195`). `tools/list` and `prompts/list` consume that catalog (`apps/overdare-ai-agent/src/mcp_router.rs:66-83`, `125-126`). Active Studio selection is stored independently in `StudioRouter.active_id` and used when resolving execution (`apps/overdare-ai-agent/src/studio_router.rs:64-69`, `145-188`); catalog selection never consults it. Catalogs can legitimately differ because each sidecar builds tools and prompts from its project config and experiment overrides (`apps/overdare-ai-agent/sidecar/src/server.ts:133-147`; `apps/overdare-ai-agent/sidecar/src/mcp-server.ts:78-90`). A current-HEAD reproduction registered two reachable Studios with distinct catalogs, selected `beta`, and received `tool_alpha` from the newer-heartbeat `alpha` record in `tools/list`. The watcher fingerprint includes live IDs, tool names, and prompt count, but not the active ID or full prompt/catalog identity (`apps/overdare-ai-agent/src/mcp_router.rs:94-112`).
**Impact and mechanism**: In a supported multi-Studio setup, the MCP client can advertise tools or prompts that the selected target does not expose and hide capabilities that it does. Calls are routed to the correctly selected Studio, so advertised-but-absent tools fail there as unknown. Selection changes may also avoid a list-change notification when the global catalog shape is unchanged. Catalog and execution therefore have different owners, making correct routing look unreliable.
**Smallest responsible action**: When an active Studio exists, derive `tools/list` and `prompts/list` from that live record's catalog. Retain the newest-record fallback only when no target is selected, so clients can discover Studio capabilities before selection. Include the active Studio ID and effective catalog shape in the watcher fingerprint so selecting, losing, or changing a target requests a re-list.
**Scope and non-goals**: Keep session-management tools router-owned and unshadowable. Preserve stale-catalog startup fallback, ambiguous-target refusal, reachability checks, and selected-sidecar execution. Do not move Studio tool behavior into Rust or introduce a new shared protocol package solely for registry serialization.
**Verification**: Register two reachable records with different tools and prompts; select each in turn and prove list responses match that record. Prove selection and selected-target loss change notification state. Preserve stale startup fallback, session-tool shadow protection, and execution-only-in-selected-sidecar coverage.
**Why now**: Multi-Studio routing is newly shipped in this range, and per-project experiment gating already provides a supported reason for catalogs to differ. Additional routed capabilities would compound failures at the same ownership split.
**Delivery**: Created issue #381 — https://github.com/overdare/diligent/issues/381

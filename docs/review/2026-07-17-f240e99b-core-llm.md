## Findings

### 1. Provider Workers Do Not Consistently Participate in Stream Cleanup

**Impact**: Immediate cleanup risk on abort or early outer-stream termination

`EventStream` exposes `setInnerWork()` and `waitForInnerWork()` specifically so consumers can wait for transport work
to settle. `ProviderManager.createDeferredExternalStream()` uses this contract and waits for the inner provider stream
in its `finally` block.

The AI SDK bridge follows the contract:

```ts
const work = runAISDKStream(stream, model, context, options, config);
stream.setInnerWork(work);
```

The OpenAI, Anthropic, ChatGPT, and retry paths instead start untracked asynchronous work:

- `packages/core/src/llm/provider/openai/index.ts:38`
- `packages/core/src/llm/provider/anthropic/index.ts:53`
- `packages/core/src/llm/provider/chatgpt/index.ts:385`
- `packages/core/src/llm/retry.ts:107`

During a normal terminal event, the worker usually returns immediately after pushing `done` or `error`. During abort,
however, `EventStream.attachSignal()` can terminate the stream before the provider SDK, fetch, decoder, or retry loop
has settled. `waitForInnerWork()` then resolves immediately for these providers because no work Promise was registered.

**Recommended correction**:

1. Add tests that hold provider cleanup behind a deferred Promise, abort the stream, and prove that
   `waitForInnerWork()` remains pending until the worker settles.
2. Store each provider's worker Promise and pass it to `setInnerWork()`.
3. Have the retry wrapper also await the active inner stream's tracked work before completing its own worker.
4. Keep the change local to each stream implementation unless repetition demonstrates that a tiny construction helper
   would reduce behavior drift.

Do not introduce a provider base class or a generic transport runner for this correction.

### 2. The AI SDK Abort Part Can Leave the EventStream Open

**Impact**: Immediate correctness risk for provider-originated aborts

`runAISDKStream()` handles two abort mechanisms differently:

```ts
if (options.signal?.aborted) return;
if (part.type === "abort") return;
```

An external signal abort also triggers `EventStream.attachSignal()`, which rejects and closes the stream. A provider
can emit an AI SDK `abort` part without the caller's signal being aborted. In that case, `runAISDKStream()` returns
without pushing a terminal provider event and without calling `stream.error()` or `stream.end()`. The worker settles,
but iteration and `result()` can remain pending.

The existing AI SDK bridge test covers text, reasoning, tools, usage, and successful finish, but not an `abort` part.

**Recommended correction**:

1. Add a simulated AI SDK stream containing an `abort` part with an otherwise live caller signal.
2. Define the existing provider contract behavior explicitly: abort should close the stream and reject with an abort
   error, matching the other provider paths.
3. Verify that no `done` event is emitted after abort and that `waitForInnerWork()` settles.

The same change is a good point to make provider state generic:

```ts
interface AISDKStreamAdapter<TState = undefined> {
  createProviderState?: () => TState;
  handleProviderPart?: (part: TextStreamPart<ToolSet>, state: TState) => ContentBlock[];
  finalizeProviderState?: (state: TState) => ContentBlock[];
}
```

The current `unknown` state forces `handleGeminiProviderPart()` and `finalizeGeminiProviderState()` to cast back to
`GeminiProviderState`. A generic adapter keeps this internal extension seam type-safe without changing any public LLM
contract.

### 3. Provider Entry Points Still Mix Independently Testable Responsibilities

**Impact**: Maintenance cost; localized rather than architectural

The recent refactor created the correct internal seams, but several implementations still keep them in one physical
file.

#### Anthropic

`provider/anthropic/index.ts` currently contains:

- SDK client and stream orchestration;
- thinking request policy;
- message conversion and tool-result coalescing;
- assistant replay filtering;
- tool schema normalization;
- provider-native web block conversion;
- final assistant-message mapping;
- error classification; and
- native compaction transport.

The conversion functions are already pure or narrowly effectful, so moving them is mostly mechanical. A reasonable
provider-local layout is:

```text
provider/anthropic/
  index.ts                 public exports and stream construction
  messages.ts              message conversion, replay, coalescing, cache breakpoints
  web-tools.ts             tool schemas and provider-native web block mapping
  native-compaction.ts     compaction request and response handling
```

Error classification may remain in `index.ts` until it has an independent reason to move.

#### OpenAI Responses stream

`provider/openai/sse.ts` combines the wire event decoder and reducer with approximately half a file of web-search,
web-fetch, citation, and completed-response fallback normalization. Extracting one provider-local `web-content.ts` or
`web-tools.ts` would leave `sse.ts` focused on:

```text
raw event -> decoded event -> accumulator transition -> ProviderEvent
```

The extraction must preserve the current completed-response fallback behavior and stay independent from the Anthropic
and Gemini web formats.

#### ChatGPT

`provider/chatgpt/index.ts` still combines diagnostic formatting, WebSocket session configuration, HTTP/SSE execution,
transport fallback policy, error classification, and native compaction. The lowest-risk first extraction is native
compaction because it is independent from the stream transport state. Diagnostics can move next if doing so makes the
HTTP and WebSocket paths easier to read without creating another lifecycle implementation.

**Test structure**:

- split `provider/chatgpt/stream.test.ts` by HTTP transport, WebSocket session behavior, retry classification, and
  Responses request compatibility;
- split `provider/anthropic/index.test.ts` into message conversion and tool-schema tests; and
- keep native compaction contract tests grouped only if the cross-provider comparison remains useful.

Every source move should preserve the current provider subpath exports through the existing `index.ts` files.

### 5. ProviderManager Cache Identity Is Broader Than Necessary

**Impact**: Small security and maintainability improvement

`StreamFactoryCache` builds its map key from:

```ts
`${provider}:${apiKey}:${imageDetail ?? ""}`
```

This duplicates the complete API key inside an internal cache-key string. It also makes invalidation scan and parse
provider-prefixed strings. A `ProviderManager` owns only one current API-key binding per provider, its provider config
is immutable after construction, and `setApiKey()` already invalidates that provider. Therefore the cache can be a
`Map<ProviderName, StreamFunction>` with direct `delete(provider)` invalidation.

Before changing it, move ProviderManager behavior tests that currently live in `packages/cli/test/provider-manager.test.ts`
into `packages/core/test/llm/provider-manager.test.ts`. Core should own tests for:

- API-key set, remove, and empty-key behavior;
- configured-provider ordering;
- stream cache reuse and invalidation;
- static native compaction lookup; and
- external-auth precedence and removal.

CLI should retain only tests for its re-export or presentation behavior.

### 6. Tool Image Decoration Is an Opportunistic Ownership Cleanup

**Impact**: Low; do not schedule as a standalone refactor

`packages/core/src/llm/image-resize.ts` correctly owns image decoding, resizing, and encoding. Its
`withImageDownscaling()` function imports the core `Tool` type only to wrap runtime-composed tools, and its sole
production consumer is `packages/runtime/src/tools/catalog.ts`.

When image handling is next changed, move the tool decorator to runtime composition while keeping the reusable image
algorithm in core. This removes the `llm/image -> tool` dependency without relocating image policy or changing the
public algorithm contract.

## Rejected Refactoring Candidates

### Do Not Introduce a Universal Provider Base Class or Descriptor

The providers now share normalized contracts but still differ materially in authentication, wire protocol, request
construction, web tools, compaction, and transport lifetime. A shared inheritance hierarchy or one descriptor object
would accumulate optional fields rather than remove demonstrated duplication.

Use provider-local sibling modules and small helpers derived from identical behavior instead.

### Do Not Redesign the Model Catalog in This Cycle

Model cards, model-class routing, provider defaults, and effort policy were separated by the latest refactors. The
current catalog is direct, tested, and small enough that linear resolution is not a measured problem. Alias-index or
immutability work can be revisited when dynamic catalogs or a larger model set create concrete pressure.

### Do Not Delete the Root LLM Barrel or Public Provider Subpaths

The explicit capability subpaths match the architecture, while the root surface remains a compatibility convenience.
Provider file decomposition can preserve both through re-exports. API removal would add migration work without helping
the internal lifecycle findings above.

### Do Not Generalize Web-Tool Normalization Across Providers

OpenAI Responses, Anthropic, and Gemini expose different source, citation, fetch, and replay semantics. Keeping their
normalizers provider-local is clearer than a cross-provider mapper whose contract would mostly be optional cases.

## Sustainability Verdict

**GREEN** — `packages/core` is currently a sustainable reusable-engine boundary. The latest range removed runtime-owned event fields, direct filesystem persistence, provider presentation text, and product policy from core while introducing capability-oriented package subpaths and a runtime import allow-list.

No broad reorganization is justified. Two ownership seams are worth removing now: runtime agent-role policy still has a name-based fallback in core, and two protocol-facing leaf payload types still have duplicate definitions. Two additional integration seams deserve the same cycle because they have concrete failure or dependency evidence: the injected tool-output store can abort the whole turn when persistence fails, and the provider retry layer imports an Agent-event serialization helper only to format logs. Public-subpath enforcement and test typechecking also need small guardrail improvements so the new boundaries remain closed.

## Structural Integrity

### Recent Core Boundary Cleanup Is Coherent
**Impact**: Positive

The four latest core refactors form one consistent ownership correction rather than churn:

- `3ff49e9c` moved provider error values to protocol-owned canonical types.
- `5da12e54` centralized provider error classification inside core.
- `08bedefd` removed collaboration and runtime status overlays from `CoreAgentEvent` and moved them to `packages/runtime/src/agent-event.ts`.
- `8e844d19` replaced direct core filesystem operations with injected `LocalImageLoader` and `ToolOutputStore` ports, moved provider presentation metadata to runtime, and replaced wildcard source exports with explicit public subpaths.

The documented boundary now mostly matches the implementation: core owns reusable providers, model resolution, the agent loop, and tool execution; runtime owns persistence, presentation, collaboration overlays, and product policy (`ARCHITECTURE.md:145-162`). `biome.json:56-83` rejects unapproved `@diligent/core/*` imports in runtime, so this is not documentation-only architecture. The rule does not currently match the bare `@diligent/core` root, however, and runtime's package barrel still uses that escape hatch; the enforcement gap is documented below.

### Runtime Agent-Role Policy Still Has a Compatibility Fossil in Core
**Impact**: Compounds over time

`packages/core/src/llm/models.ts:397-405` contains `agentTypeToModelClass(agentType, parentModel)`, including the runtime role name `"explore"` and its policy decision to use a `lite` model. Agent role definitions and their defaults now belong to runtime:

- `packages/runtime/src/agent/agent-types.ts:50-95` defines built-in role policy.
- `packages/runtime/src/agent/agent-types.ts:97-113` materializes `explore.defaultModelClass = "lite"`.
- `packages/runtime/src/agent/resolved-agent.ts:5-13` carries the resolved default as runtime metadata.
- `packages/runtime/src/collab/registry.ts:269-275` still falls back to the core helper after reading that metadata.

The fallback is redundant for current built-ins: `explore` already supplies `lite`, while an unspecified custom agent should inherit the parent model class without core knowing its name. Keeping the helper makes future role additions appear to require a core edit and can silently mask missing runtime metadata.

**Cheaper fix now**: remove `agentTypeToModelClass` from the core model registry and resolve `explicit override → resolved agent default → parent model class` entirely in runtime. Keep `resolveModelForClass()` and `getModelClass()` in core because provider-neutral model capability resolution is genuinely engine-level.

### Core and Protocol Duplicate Two Cross-Boundary Leaf Types
**Impact**: Compounds over time

Core locally defines `MessageDelta` and `SerializableError` at `packages/core/src/agent/types.ts:20-36`. Protocol defines structurally equivalent canonical wire types at `packages/protocol/src/data-model.ts:106-124`.

This duplication has already required synchronized edits:

- `4ba0be37` added `content_block_delta` to both event surfaces.
- `93a47a01` added `providerErrorReason` to both core `SerializableError` and the protocol schema.

The duplication is inconsistent with the current type-flow rule. Core already imports protocol-owned message types and provider error values (`packages/core/src/types.ts:1-15`, `packages/core/src/llm/types.ts:1-25`), and the March 23 review explicitly recorded protocol as canonical for cross-package types. The full `CoreAgentEvent` union should remain core-owned because it contains internal events such as `prompt_signature` and `context_injected`; only the identical serializable leaf payloads need one owner.

**Cheaper fix now**: alias or import `MessageDelta` and `SerializableError` from `@diligent/protocol` in `packages/core/src/agent/types.ts`. If direct aliasing is intentionally rejected, add compile-time equality assertions analogous to `packages/core/src/llm/provider-name.typecheck.ts` so drift fails typecheck instead of surfacing during a later protocol change.

Aliasing the TypeScript shape is not sufficient by itself: a newly optional protocol field does not force `toSerializableError()` to populate it. Add mapping or serialization coverage that exercises every provider diagnostic field so type ownership and runtime behavior cannot drift independently.

### The Injected Tool-Output Store Is Not Failure-Isolated or Storage-Neutral
**Impact**: Immediate reliability risk at an integration boundary

`8e844d19` correctly moved temp-file creation out of core behind `ToolOutputStore`, but `packages/core/src/tool/executor.ts:77` awaits `outputStore.save()` outside the tool-execution error boundary. A diagnostic store whose `save()` throws causes `executeTool()` itself to reject instead of returning the already available truncated result. A targeted reproduction with a 60 KB tool result and a throwing store produced `REJECTED:store unavailable`; the existing executor tests cover a successful store and the absence of a store, but not a failing store.

The port is also only partially abstract. Its name is storage-neutral, while core interprets the returned string as a filesystem path and emits both `"Full output saved to disk"` and `metadata.fullOutputPath`. That makes a database, object store, or in-memory implementation dishonest even though the interface appears to permit one.

**Cheaper fix now**: add the failing-store test first, make optional persistence best-effort so truncation still succeeds, and make the contract honest. Either name and type it as a file store returning a path, or return a structured storage receipt whose reference, notice, and metadata are supplied by the adapter. Preserve the current path metadata where runtime compatibility requires it.

### Provider Retry Reaches Up Into Agent Event Serialization
**Impact**: Small today, compounds when diagnostics evolve

`packages/core/src/llm/retry.ts:4` imports `toSerializableError()` and `formatSerializableErrorForLog()` from `packages/core/src/agent/util/errors.ts`. The intended dependency direction is Agent orchestration → provider retry. The current logging path reaches back upward:

```text
ProviderError → Agent event serializer → retry log string
```

Retry does not emit `CoreAgentEvent`; it uses the serializer only to format diagnostics. This couples retry logging to the consumer-event payload and means a change to Agent serialization can affect a lower-level provider mechanism. The current static import graph has no cycle, but this is its only `llm → agent` edge.

**Cheaper fix now**: keep `toSerializableError()` at the Agent/consumer event boundary, and format `ProviderError` directly inside retry or through a neutral error-formatting module. Do not move the whole Agent serializer into the provider layer merely to remove the import.

## Cross-Package Coherence

### Explicit Core Subpaths Match Consumer Responsibilities but Are Not Fully Sealed
**Scope**: `packages/core`, `packages/runtime`

`packages/core/package.json:6-20` exposes capability-oriented subpaths, and runtime imports predominantly through `agent`, `message-contract`, `model-registry`, `provider-contract`, and `tool-contract`. This is a meaningful improvement over wildcard source exports because internal file movement no longer changes the de facto package API.

The broad root export remains acceptable as a convenience surface for external and compatibility consumers. It should not be deleted merely for aesthetic purity. Internal usage should still migrate to the intended subpaths, and lint should reject bare `@diligent/core` imports inside runtime after `packages/runtime/src/index.ts` is rewritten to re-export from explicit subpaths. The current `@diligent/core/*` restriction does not match the bare root, so it can be bypassed accidentally.

The subpath entry files also use `export *` internally (`provider-contract.ts`, `model-registry.ts`, `image-contract.ts`, and `tool-contract.ts`). This means adding an exported helper to an implementation module can silently enlarge the public contract. For example, `model-registry` currently exposes provider-specific `GEMINI_THINKING_BUDGETS`, while `image-contract` exposes conversion helpers used only inside provider materialization. Replace wildcard symbol exports with explicit type/value lists when these entrypoints are next touched. This is a small API guardrail, not a reason to split `provider-contract` or delete the root compatibility surface.

### Protocol Leaf-Type Duplication Is the Remaining Type-Flow Exception
**Scope**: `packages/protocol`, `packages/core`, `packages/runtime`

Provider names, provider error values, messages, content blocks, and usage types now flow from protocol into core. `MessageDelta` and `SerializableError` are the remaining identical leaf contracts that cross the same boundary without direct ownership reuse. Consolidating only these types preserves the useful distinction between core engine events and richer runtime/protocol events introduced by `08bedefd`.

## Forward Compatibility

### Agent Role Additions Should Not Touch the Engine Package
**Horizon**: Breaks when a new built-in role needs a different default model class or role names change

Runtime already has the correct metadata channel through `ResolvedAgentDefinition.defaultModelClass`. Leaving a name-based fallback in core creates two policy locations and makes role onboarding ambiguous. Removing it now is a small deletion; waiting until more roles exist turns it into a compatibility decision across custom agents, built-ins, and core exports.

### Error Diagnostics Will Continue to Evolve
**Horizon**: Breaks when the next provider error field is added

The latest range added `providerErrorReason` and then `usage_limit_reached`, demonstrating that the diagnostic payload is active rather than frozen. Reusing protocol's `SerializableError` type in core prevents every new optional diagnostic from requiring coordinated structural edits in both packages while leaving runtime presentation (`ClientError`) separate.

### Optional Persistence Must Not Become Turn-Critical by Accident
**Horizon**: Breaks on temp-directory exhaustion, permissions errors, or a future remote store outage

Tool-output persistence exists to preserve the untruncated artifact after core has already produced a usable bounded result. Unless the product explicitly decides that full-output storage is mandatory, adapter failure should degrade to the truncated result rather than convert a successful tool call into a fatal Agent error. The current port does not encode or test that policy, so infrastructure behavior can silently decide turn semantics.

## Verification Guardrails

### Core Tests Execute but Are Not Typechecked
**Impact**: Boundary contract drift can pass the normal verification path

`packages/core/tsconfig.json:6` includes only `src/**/*`. Bun executes the tests by transpiling them, but the repository typecheck never checks `packages/core/test`. A concrete stale fixture exists at `packages/core/test/tool/executor.test.ts:9-14`: it returns a `ToolContext` with the removed `approve` field and without the required `abort` callback. All 435 core tests pass, while a targeted TypeScript check of that test reports `TS2353` for `approve`.

This is directly relevant to boundary refactoring: public contract tests can continue executing with structurally stale fixtures and therefore fail to protect the contract they claim to exercise.

**Cheaper fix now**: add a test-specific TypeScript config that includes `src/**/*` and `test/**/*`, invoke it from the root typecheck, and correct the stale fixture. Keep build/declaration output scoped to source by retaining the existing production config separately.

## Novel Perspective

### A Redundant Fallback Can Be More Dangerous Than a Missing Abstraction

- **Why no one has seen this**: `agentTypeToModelClass()` predates the core/runtime split and reads like a generic model helper because it accepts `string`. After resolved agent metadata was introduced, its `"explore"` branch became unnecessary for built-ins but remained as a compatibility fallback.
- **Evidence**: Runtime resolves `defaultModelClass` before calling the helper (`packages/runtime/src/collab/registry.ts:269-275`), and built-in `explore` already supplies `lite` (`packages/runtime/src/agent/agent-types.ts:107-113`). The only remaining behavior for roles without metadata is parent-class inheritance.
- **Implication**: Boundary reviews should look for old fallbacks that survived decomposition, not only imports in the wrong direction. Such fallbacks hide incomplete metadata and preserve obsolete ownership after the main code has moved.

## Rejected Refactoring Candidates

### Do Not Split `provider-contract` Merely Because It Exports `ProviderManager`

`ARCHITECTURE.md:149-155` explicitly assigns `ProviderManager` and stream proxying to core, and `packages/core/src/provider-contract.ts:1-7` accurately describes that provider-engine boundary. The name means “public provider contract for consumers,” not “type-only declarations.” No incorrect dependency direction was found.

### Do Not Introduce a Universal Provider Descriptor or Transport Framework Yet

Provider names, runtime auth descriptors, model metadata, static environment resolution, and authenticated stream construction have different owners. A single descriptor spanning protocol, core, and runtime would either import runtime presentation into core or turn one registry into an oversized optional-field object. Current provider onboarding is explicit, and the July 3 “watch at 10+” threshold has not been reached.

Likewise, only ChatGPT currently uses the WebSocket path, and it is opt-in. A cross-provider WebSocket abstraction still lacks a second concrete implementation from which to derive shared semantics.

### Do Not Delete the Root Barrel; Seal Internal Usage Instead

The root surface still serves CLI and compatibility consumers, so deleting it would create migration churn without proportionate benefit. That does not justify internal use of the escape hatch. Rewrite repository-owned imports to use explicit subpaths, add a bare-root restriction for runtime, and leave removal of the external compatibility surface to a separately justified API-version decision.

### Consolidate `ToolRenderPayloadLike` Only Opportunistically

The same weak carrier shape appears in `packages/core/src/types.ts:17-23` and `packages/core/src/tool/types.ts:34-45`. It should eventually have one core owner, but there is no observed drift and the deliberately weak `blocks: unknown[]` shape prevents protocol rendering semantics from entering core. This is not worth a standalone task; consolidate it when either file next changes.

## Findings

### F-01 — ChatGPT drops caller output controls

**Disposition**: Act now
**Lens**: Contract | Operational correctness
**Confidence**: High
**Evidence**: `StreamOptions` defines `maxTokens` and `temperature` at `packages/core/src/llm/types.ts:84-88`. The Agent supplies a resolved `maxTokens` on every provider request at `packages/core/src/agent/assistant.ts:106-112`. The shared Responses request builder accepts both values and maps them to `max_output_tokens` and `temperature` at `packages/core/src/llm/provider/openai/responses.ts:253-296`, and the OpenAI provider forwards both at `packages/core/src/llm/provider/openai/index.ts:43-55`. ChatGPT uses the same builder but omits both fields at `packages/core/src/llm/provider/chatgpt/index.ts:316-328`; the resulting body feeds both HTTP and WebSocket transports. Current ChatGPT request tests exercise transport, reasoning, Lite conversion, and terminal `max_output_tokens` responses, but do not assert outgoing output controls.
**Impact and mechanism**: ChatGPT callers cannot enforce the shared output-token budget or temperature contract. In normal Agent turns, `resolveMaxTokens()` is computed and then discarded at the provider boundary, allowing provider defaults to exceed Diligent's intended output budget and increasing latency and context pressure. Direct callers that set `temperature` see the same silent loss. The omission occurs before transport selection, so both HTTP/SSE and WebSocket requests are affected.
**Smallest responsible action**: Forward `options.maxTokens` and `options.temperature` into the existing `buildResponsesRequestBody()` call in the ChatGPT provider. Add request-body coverage proving both standard Responses and Responses Lite/WebSocket paths preserve supplied fields and omit them when undefined.
**Scope and non-goals**: Limit the change to ChatGPT request construction and focused provider tests. Do not change model cards, `resolveMaxTokens()`, retry behavior, transport selection, or the shared Responses builder.
**Verification**: Tests must observe `max_output_tokens` and `temperature` in the outgoing HTTP request and WebSocket `response.create` payload when supplied; verify `max_output_tokens` receives the Agent-resolved value in an Agent-to-ChatGPT request; verify undefined fields remain absent; keep existing Lite conversion and transport tests green.
**Why now**: Commit `0536cd19` deliberately consolidated both ChatGPT transports around one request body. The fix is now one bounded forwarding change; additional models and callers would otherwise build on a provider implementation that advertises but silently ignores the shared options.
**Delivery**: Created issue #318 — https://github.com/overdare/diligent/issues/318

### F-02 — Anthropic fetch replay invents enabled citation state

**Disposition**: Act now
**Lens**: Contract | Operational correctness
**Confidence**: High
**Evidence**: Anthropic fetch request construction preserves `citationsEnabled`, including `false`, at `packages/core/src/llm/provider/anthropic/web-tools.ts:42-51`, and the request test asserts `{ citations: { enabled: false } }` at `packages/core/test/llm/provider/anthropic/thinking.test.ts:249-280`. Result normalization then unconditionally stores `citationsEnabled: true` at `packages/core/src/llm/provider/anthropic/web-tools.ts:109-132`. The response fixture explicitly carries `citations: null` at `packages/core/test/llm/provider/anthropic/web-tools.test.ts:156-176`, yet its expected normalized block asserts `true` at lines 246-264. Replay converts the normalized boolean back to Anthropic `{ citations: { enabled: true } }` at `packages/core/src/llm/provider/anthropic/messages.ts:256-286`, with tests encoding that replay at `packages/core/test/llm/provider/anthropic/messages.test.ts:390-405` and `463-475`.
**Impact and mechanism**: A fetch requested with citations disabled, or a result for which citation state is unknown, is persisted as citation-enabled. On the next Anthropic turn, replay sends a historical fetch document with `{ citations: { enabled: true } }`, changing the meaning of provider-native history. This is a deterministic round-trip defect across request construction, normalization, JSONL persistence, and same-provider replay; the current separated request and response tests mask the contradiction.
**Smallest responsible action**: Stop hardcoding `true`. Preserve only citation state that is actually known. If the Anthropic result carries an explicit boolean, normalize it. When the result does not echo the setting, correlate the fetch result's `tool_use_id` with the stream-local fetch request configuration and persist that selected boolean; otherwise omit `citationsEnabled` rather than inventing a value.
**Scope and non-goals**: Preserve the existing optional boolean and provider-native block shape. Do not redesign provider-native content, add frontend presentation, or broaden Anthropic web-tool capability.
**Verification**: Add an end-to-end focused matrix that constructs Anthropic fetch tools with citation settings `false`, `true`, and unspecified; normalizes the corresponding provider result; round-trips the block through session persistence; and replays it through `convertMessages()`. Replay must preserve `false` and `true`, and omit the field when state is unknown. Existing web search and foreign-provider replay behavior must remain unchanged.
**Why now**: Typed Anthropic fetch configuration and same-provider replay landed together in `0536cd19`. Correcting the carrier now is localized; adding more provider-native fetch fields while request and result state are already contradictory would multiply replay ambiguity.
**Delivery**: Created issue #319 — https://github.com/overdare/diligent/issues/319

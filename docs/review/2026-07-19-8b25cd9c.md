## Findings

### F-01 — Implicit child model class is not durable across restart

**Disposition**: Act now
**Lens**: Contract | Operational correctness
**Confidence**: High
**Evidence**: `spawn_agent` makes `model_class` optional and documents that a general child defaults to the parent class at `packages/runtime/src/collab/spawn-agent.ts:24-30`. At spawn time, `AgentRegistry` resolves the effective class from restored policy, explicit input, the agent default, or the current parent model, then stores it in `CollabResumePolicy` at `packages/runtime/src/collab/registry.ts:254-266`. Persisted restoration reconstructs `modelClass` only from the original explicit `model_class` input at `packages/runtime/src/session/collab-session-handler.ts:51-63`. If that input was omitted, `restoreAgent()` re-derives the class from the current agent definition or current parent model at `packages/runtime/src/collab/registry.ts:733-747`.
**Impact and mechanism**: A child spawned without `model_class` can resume under a different class after an app-server restart. For example, a general child that implicitly inherited a pro parent can be restored as general if the parent selection changes before restart. The persisted child identity therefore does not preserve the effective model-class policy used when the child was created.
**Smallest responsible action**: Persist the already-resolved `CollabResumePolicy.modelClass` with the successful spawn result, preferably as persisted tool-result metadata rather than LLM-facing output. Make `CollabSessionHandler` prefer this resolved value while retaining raw spawn-argument inference for legacy sessions.
**Scope and non-goals**: Cover the resolved model class only. Preserve existing sessions. Do not redesign collaboration persistence, change model-class routing, add a frontend or protocol field, or broaden this action to the full effective child tool envelope.
**Verification**: Add an app-server restart regression that spawns a general child under a pro parent without `model_class`, restarts with a general parent, resumes the child without policy overrides, and proves the original pro class remains effective. Preserve explicit policy mismatch and escalation rejection coverage, and prove legacy raw-input inference still works when resolved metadata is absent.
**Why now**: The range strengthens and evaluates immutable child resume behavior, but current coverage uses stable explicit or role-default classes and misses parent-class drift. Further collaboration resume work would otherwise build on a continuity guarantee that is not durable for omitted inputs.
**Delivery**: Created issue #321 — https://github.com/overdare/diligent/issues/321

### F-02 — Registry refresh drops child output-store and loop-hook ownership

**Disposition**: Act now
**Lens**: Ownership | Contract
**Confidence**: High
**Evidence**: Initial app-server collaboration assembly supplies both the selected output store and bundled child loop-hook factories at `packages/runtime/src/app-server/factory.ts:149-165`. After mode and host filtering, the same factory calls `registry.updateDeps()` without either dependency at `packages/runtime/src/app-server/factory.ts:197-213`. `AgentRegistry.updateDeps()` explicitly assigns `agentLoopHookFactories` from the omitted update and does not carry `toolOutputStore` as a mutable field at `packages/runtime/src/collab/registry.ts:157-193`. Child construction consequently receives no bundled loop hooks and falls back to the production output store at `packages/runtime/src/collab/registry.ts:360-383`. Existing registry tests prove these dependencies only when constructing `AgentRegistry` directly at `packages/runtime/test/collab/registry.test.ts:186-211` and `packages/runtime/test/collab/registry.test.ts:1221-1263`; the factory test verifies the injected store only on the main agent at `packages/runtime/test/app-server/factory.test.ts:151-175`.
**Impact and mechanism**: The normal app-server path silently discards assembly-owned child capabilities before the first child spawn. Eval or host-injected output stores are not used by children, breaking registered-read isolation and output ownership. Bundled child loop hooks also do not run, despite the main/child hook assembly contract. Direct registry tests remain green because they bypass the destructive refresh.
**Smallest responsible action**: Preserve `toolOutputStore` and bundled `agentLoopHookFactories` through the post-filter registry refresh. The smallest fix may pass both values in the current `updateDeps()` call, or make the update explicitly patch-based so omission preserves existing assembly-owned dependencies.
**Scope and non-goals**: Keep mode-filtered `parentTools` authoritative for child access. Do not redesign `AgentRegistry`, change hook ordering, tool catalogs, output-store interfaces, approval behavior, or introduce global state.
**Verification**: Add factory-level coverage that creates an app-server agent and spawns a child. Prove the child and nested registry retain the injected output store; bundled hook factories receive `agentKind: "child"` and create fresh instances per child; main-agent hook ordering remains unchanged; and mode-filtered parent tools still govern child access.
**Why now**: The range explicitly added eval output-store ownership and deterministic child-hook coverage, but the production assembly boundary bypasses both guarantees. Leaving this gap makes unit-level composition disagree with the actual app-server path.
**Delivery**: Created issue #322 — https://github.com/overdare/diligent/issues/322

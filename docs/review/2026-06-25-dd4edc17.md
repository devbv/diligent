## Forward Compatibility

### Versioned Runtime Updates — Well-Architected But Large
**Horizon**: Stable for current needs; migration logic will persist long-term

`apps/overdare-ai-agent/src/update.rs` (1,530L) implements versioned runtime directories (`updates/runtime-v{version}/`), atomic active-pointer files, pinned version support, and legacy flat→versioned migration. The feature is architecturally sound — it solves the atomic-update problem correctly with version-isolated directories and JSON metadata pointers.

The 1,530-line file is the largest single source file in the Rust launcher. Natural split points: manifest fetching/validation (~300L), filesystem operations (~350L), migration logic (~250L). Not urgent but worth noting for future maintenance.

### Privacy Policy URL Caching — In-Memory Only
**Horizon**: Breaks when multiple processes serve the same user state

`packages/runtime/src/config/consent.ts` caches the resolved privacy-policy URL in a module-level variable (`cachedPrivacyPolicyUrl`). The cache has no TTL — once resolved, it persists for the process lifetime. If the privacy policy is updated server-side, running instances will serve stale URLs until restarted. The `resetPrivacyPolicyUrlCache()` test helper exists but there's no production refresh path.

This is acceptable for the current single-process model but would need attention for long-running server deployments or multi-process architectures.

### Bundled Tool Provider Hooks — Fixed Set
**Horizon**: Breaks when a bundled provider needs a lifecycle event not in the current 3-hook set

`BundledToolProvider` (44L) supports 3 hook types: `onUserPromptSubmit` (sync), `onStop` (sync), `onEntryAppended` (async). Adding a new hook point requires modifying the interface, `CollectedBundledHooks`, and the hook collection logic in the catalog. This is a minor friction point — the interface is clear and well-documented — but it prevents bundled providers from subscribing to arbitrary lifecycle events.

For comparison, the plugin hook system uses `PluginHookFn` arrays that are dynamically collected. Bundled providers could adopt the same pattern if the hook set needs to grow beyond 5-6 types.

### App-Server Factory as Coordination Bottleneck
**Horizon**: Breaks when a new subsystem requires factory-level wiring

`packages/runtime/src/app-server/factory.ts` (206L) wires 6 subsystems: agent creation, tool building, consent backend, model persistence, mode application, and skill guardrails. Each new cross-cutting concern (e.g., observability, rate limiting, usage quotas) will need factory integration. The factory is clean now but its growth trajectory mirrors the pre-decomposition SessionManager — it works by being small enough to hold in one mental model.

### The Passion-Junior Automation Pipeline Has Become a Silent Architecture Enforcement Mechanism

- **Why no one has seen this**: Previous reviews noted passion-junior as a "delivery engine" (2026-06-04) and tracked its PR output quantitatively. What hasn't been examined is its effect on architectural discipline — specifically, whether automated issue resolution produces structurally different outcomes than manual development.

- **Evidence**:
  1. **Structural decomposition quality**: The 5 resolved issues in this cycle all required multi-file coordination. Commit 7f5557a9 (SessionManager decomposition) touched 8 files across `packages/runtime/src/session/` and created 5 new modules with clean interfaces. Commit 4003b827 (tool catalog pipeline) restructured a 418-line monolithic function into 5 phases. Both are non-trivial architectural changes that landed correctly on the first try.

  2. **Issue-to-implementation fidelity**: Every resolved issue (#150–#154) matches the priority action specification from the review document almost exactly. The OAuth router extraction (#150) produced a 35-line file as specified. The App.tsx extraction (#154) hit the "under 200 lines" target (274L — reasonable given consent additions). The tool catalog (#153) adopted the exact phase names suggested.

  3. **Zero rework after automation**: None of the 5 automated PRs required follow-up fixes. Compare to manual feature work which generates a 2-4 commit "fix tail" (the pattern identified in the previous review's Novel Perspective).

  4. **Time compression**: All 5 structural improvements landed within 6 days of the review (commits between 4c3d8d0a review commit and e606201c cleanup). Manual structural work in previous cycles took 2-3 weeks when it happened at all (often deferred).

- **Implication**: The passion-junior pipeline is not just automating code changes — it is enforcing the tech-lead review's architectural recommendations with higher fidelity and lower latency than manual development. This creates a feedback loop: the review specifies decomposition boundaries → automation implements them exactly → the next review finds clean structure.

  The risk is over-reliance: if the review specifies an incorrect decomposition boundary, automation will implement it faithfully rather than pushing back. The tech-lead review must be more careful about recommendations, because they will be executed literally. Conversely, this makes the review's architectural specifications higher-leverage — investing more time in precise action specifications yields direct structural returns.
